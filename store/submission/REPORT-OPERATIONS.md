# Content report operating checklist — publisher action, not an automated service

Before public submission, confirm that ahmedbecetti41@gmail.com is owned, works, and is monitored. Test both an email-client report and the copy-to-email fallback on Windows. Record only necessary information in the publisher's chosen private support system; no message contents or personal information belong in this repository.

For a received report:
1. Acknowledge through the support inbox according to an achievable publisher-defined response policy. Do not promise an SLA that is not staffed.
2. Review only the information the reporter chose to send. Never request passwords, sign-in tokens, unnecessary personal data or entire confidential PDFs.
3. Determine the affected tool/provider and severity. Avoid downloading or duplicating illegal material; follow applicable reporting/legal obligations, especially child-safety concerns.
4. Reproduce safely with sanitized data if appropriate. Review provider terms and safety controls. Escalate to the provider or restrict/disable unsafe generation paths if needed.
5. Communicate the outcome when appropriate and review repeated patterns. Remove any retained report data when no longer necessary, subject to lawful obligations.
6. Update the privacy notice, policy disclosures and Store listing if data handling or capabilities change.

Before release, perform and record content-safety tests across all enabled providers, including relevant languages. The current application does not implement its own comprehensive model moderation layer or a public user-content gallery. Provider safeguards must be verified, not assumed. If adequate safeguards cannot be demonstrated for a feature, do not submit it as an enabled compliant feature. The reporting control alone does not establish compliance with Microsoft Store content policies.
